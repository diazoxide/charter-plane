# charter-app M2.26: porting charter's `_shared_rels` found three fidelity

_2026-09-21 04:13 · persistent_

charter-app M2.26: porting charter's `_shared_rels` found three fidelity defects M2.24 left, each measured against the pinned charter-cp oracle first. (1) `guest::planned` used `symlink_metadata().is_err()` for "missing", so EACCES read as "not there" and charter-app would WRITE over a path it could not read — only ENOENT/ENOTDIR prove a path gone (charter's `_exists`, ruling G(e)). (2) `planned` read a generated path through a committed `.claude -> <outside>` link and reported the plane's rules in force through a link `write_into` refuses — charter asks `_inside` BEFORE it reads. (3) `harness-edited` was reported as `harness-behind`: when charter's record still settles on exactly what the plane wants, the harness only ADDED to the file and the oracle says "Up to date — nothing to do"; `harness-behind` is what it says once the plane has moved on. Also: charter republishes NOTHING when the record it would publish equals the record it read, so a `.charter-generated` it drops as untrusted (a key that walks out of the checkout) is left byte for byte on disk — charter-app overwrote it on every wire. And a CHECKOUT is `git_dir(p).is_some()`, never `p.join(".git").exists()`: a linked worktree whose admin directory is unreadable is passed over by charter and was reported `blocked` by the shallow test.
