Measured 2026-09-15, claude 2.1.272, for exit-gate task 1. (1) '--session-id <uuid>' is reported as-is at SessionStart, but transcript_path does not exist until the first prompt. (2) '--resume <uuid> --name X' keeps the same session_id (source=resume) and renames the session; the 'claude --resume' picker shows X, while in-session /resume hides the current session. (3) '--resume' combined with '--session-id' is refused (exit 1) unless --fork-session is also given. (4) A nested claude inside a chat fires its own SessionStart with a new session_id and an identical inherited env (CLAUDECODE, TMUX_PANE, CHARTER_*); only CLAUDE_PID tells it apart. The nested claude sets CLAUDE_PID to its own pid; a Bash-tool child inherits the outer claude's CLAUDE_PID. CLAUDE_PID is NOT reliably the hook's parent: Claude runs every hook as '/bin/sh -c <command>'. bash execs a lone command, so getppid()==CLAUDE_PID there, but compound forms leave one or two sh processes in between (reading C7, 0 prompts). (6) CLAUDE_CODE_SESSION_ID is set in hook env, equals the payload's session_id, and follows /clear, while CLAUDE_PID stays the same. Ruling built on this: a report is the chat's own when CLAUDE_CODE_SESSION_ID == payload.session_id AND (its session_id is the recorded id, which adopts its CLAUDE_PID, OR its CLAUDE_PID is the adopted one). (7) '!' in the TUI costs a model turn in 2.1.272, and two tmux send-keys C-c at startup did not end claude. (5) /clear fires SessionStart with source=clear and a new session_id, yet --resume <old uuid> still restores the pre-clear conversation. Codex 0.147.0 fires SessionStart at the first turn, not at launch (read from source). Isolation gotcha: a throwaway CLAUDE_CONFIG_DIR is logged out; with the real config dir, excluding user settings still loads user MCP servers from ~/.claude.json in nested 'claude -p' runs, so put a PATH stand-in for charter first.
