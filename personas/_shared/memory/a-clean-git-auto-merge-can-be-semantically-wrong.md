# A CLEAN git auto-merge can be semantically wrong, and the import line is

_2026-09-23 00:12 · persistent_

A CLEAN git auto-merge can be semantically wrong, and the import line is where it bites. Hit 2026-09-22 merging main into charter-app's m610-3-gauges and m610-4-trend: main had REMOVED the last use of a type and therefore dropped it from an import ('import { movedAt, quietOnes, stateOf, useChatStates } from "./chatState"'), while the branch still had 'states: ChatStates' further down. Neither side edited the other's line, so git raised NO conflict, took main's shorter import, and produced a file that does not compile - 'TS2304: Cannot find name ChatStates'. CI's web job caught it; nothing local would have, because I never typechecked after the merge. THE RULE: after merging into a TypeScript/Rust branch, run the typechecker before pushing, even when the merge was clean - 'no conflicts' says the two sides did not touch the same LINES, never that the result is coherent. The shape to watch for is one side removing a symbol's last use while the other adds one; the import line then belongs to whichever side git saw last and nothing checks it against the body. Same class as a hand-merged bindings.ts: regenerate or verify, never trust the textual merge.
