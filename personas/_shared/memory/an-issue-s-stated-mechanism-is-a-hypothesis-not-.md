# An issue's stated MECHANISM is a hypothesis, not a finding - brief agent

_2026-09-23 03:16 · persistent_

An issue's stated MECHANISM is a hypothesis, not a finding - brief agents to treat the ticket as the symptom and re-derive the cause. Measured over one night (2026-09-22/23) on charter-app, where agents were briefed with exactly that instruction: FOUR of the tickets worked had premises that did not survive contact with the code. #90 framed a numbering hazard as 'a NEW chat inherits a closed chat's pointer'; the real mechanism is that the number names a chat's POSITION in the reopen record, so closing any chat shifts every later one down and a chat the operator LEFT OPEN comes back wearing another's workspace and lock - no new chat needed. It also recorded a trade-off ('a durable id would lose the workspace selection') that does not exist, because the record already outlives the app. #127's three named commands had already been fixed in passing by an unrelated commit that never mentioned the issue, and the real defect was a FOURTH command the audit found. #89's stated reason was wrong about the Python oracle (hooks.py never calls glstate.maybe_spawn) though its conclusion survived for a different reason. #178 was filed as if nothing behind the button existed while a sibling agent was building it. THE RULE: put 'treat the issue as the statement of the symptom, not as the diagnosis - if its account of the mechanism is wrong, say so in the PR' in every fix brief, and post the refutation as an issue comment BEFORE the PR closes it, or the history reads as if the ticket was right.
