# A token MINTED INSIDE a process tree cannot prove which process in that

_2026-09-23 12:27 · persistent_

A token MINTED INSIDE a process tree cannot prove which process in that tree asked - so 'a single-use token lets only the approved invocation act' is FALSE for anything a harness runs. Refuted 2026-09-23 on charter-app#204, after I had offered it to the operator as a guarantee and he ruled on it. The property wanted was: the approved 'charter handoff' can open a chat through the app's hook socket, and a second process in the same chat's tree cannot. No such fact exists: anything the invocation mints, a sibling mints identically (same user, same env incl. CHARTER_HOOK_SOCKET, same filesystem); anything the app hands over travels by env/file/argv/inherited fd, all readable tree-wide; kernel peer creds prove only that the peer RAN charter, and a sibling can exec 'charter handoff' itself; and the operator's approval happens in the harness's permission prompt, which NO hook witnesses between approval and execution. The only construction with a real boundary puts the witness OUTSIDE the tree (the window asking). What a ticket honestly buys: one socket line opens nothing, replay is useless, one approval opens at most one chat. LESSON BEYOND THE CASE: before calling a new capability 'a larger primitive', count what the tree can ALREADY do - an in-tree process can already run 'claude -p "..."' headless with the operator's authority, so a VISIBLE tab adds no reach; visibility, not a token, was the real control. Recommending a security guarantee without checking it can be built is how the operator ends up ruling on a false premise.
