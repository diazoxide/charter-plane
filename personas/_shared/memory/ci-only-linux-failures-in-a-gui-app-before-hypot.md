# CI-only Linux failures in a GUI app: before hypothesising, make the app

_2026-09-18 12:18 · persistent_

CI-only Linux failures in a GUI app: before hypothesising, make the app say how far it got. charter-app M1.7 (2026-09-18) spent three ~10-minute CI round trips guessing (tray? single-instance? WebKit?) at a Linux app that started, stayed alive 30s and never reached Tauri's setup hook. One env-gated marker log (CHARTER_LAUNCH_LOG, printing each startup step with elapsed ms, same pattern as the existing CHARTER_BENCH_LOG) answered it on the first try: 'building' 1ms -> 'built' 25071ms, and 25062ms on the next launch. Two launches agreeing to 9ms is a TIMEOUT, not work — and 25000ms is D-Bus's default reply timeout. Cause: bare 'xvfb-run' gives no session bus. Fix for CI: 'dbus-run-session -- xvfb-run -a ...' (a real Linux desktop has a bus; testing without one tests a machine nobody uses) and add dbus-x11 to the apt list. The product cost is separate and was filed as charter-app#24: 25s cold start on any bus-less Linux, against a 2s limit. Generalise: a suspiciously round elapsed time (25s, 30s, 90s, 120s) is a timeout to look up, not slow code to optimise.
