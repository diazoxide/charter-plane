# macOS display state silently invalidates any GUI benchmark or e2e test t

_2026-09-18 00:27 · persistent_

macOS display state silently invalidates any GUI benchmark or e2e test that waits for a paint. Four ways, all measured in charter-app M0.6 (2026-09-17): (1) a COVERED window gets no requestAnimationFrame at all; (2) a SLEEPING display the same; (3) a LOCKED screen the same (ioreg -n Root -d1 -r -a contains CGSSessionScreenIsLocked); (4) worst because it looks like data — an IDLE display DROPS ITS REFRESH RATE, and nothing can draw more often than the display changes, so one run read xterm.js's DOM renderer at 22 draws/s where the page was only getting 26 frames/s, and paint latencies inflated because each paint waits one more frame (80 ms at 12 Hz vs 16 ms at 60). Fixes: bring the window front by pid (osascript 'set frontmost of (first process whose unix id is N)'), 'caffeinate -d -i -u -w <pid>' (-u is the one that holds the refresh rate; 'caffeinate -u' DOES turn an off display back on (man caffeinate: "If the display is off, this option turns the display on"), verified 2026-09-18 when a bench run that had failed with zero frames ran at a full 60 fps after 'caffeinate -u -t 3'), and record the page's own frames-per-second beside every draw measurement, refusing to measure below ~50.
