# WebDriver in charter-app's scenario suite dispatches a SYNTHETIC DOM KEY

_2026-09-23 03:27 · persistent_

WebDriver in charter-app's scenario suite dispatches a SYNTHETIC DOM KEYDOWN AND PERFORMS NO DEFAULT ACTION OF ANY KIND. That single fact is the cause of three symptoms that were catalogued separately for a day before anyone joined them: (1) Enter on a focused <button> does not activate it; (2) Tab does not move focus; (3) browser.keys(['Shift','Tab']) arrives with shiftKey false, i.e. not as a chord. Measured 2026-09-23 in a REAL WKWebView (webkit 605.1.15, macOS, app built with tauri build --features e2e), not inferred: two plain text <input>s were injected into the running window and Tab moved focus between them not at all, while the keydown arrived unprevented - and WebKit tabs between text fields regardless of the full-keyboard-access gate, so no engine-side explanation survives. WHAT THIS MEANS FOR TEST DESIGN: any claim about what a KEY DOES belongs in jsdom, which implements activation and focus navigation; a scenario can only assert what the key's absence leaves behind. But a scenario still proves one thing jsdom cannot and it is worth writing: that an attribute or handler SURVIVED THE VITE BUILD and is on the element in the shipped app - a transform that dropped a tabindex would leave every jsdom test green and the window exactly as broken as before. Recorded in docs/ui-primitives.md with the trace. Do not re-derive this from a fourth symptom.
